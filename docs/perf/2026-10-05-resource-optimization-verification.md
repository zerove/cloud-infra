# 资源优化的效果量化：**判据不成立**（2026-10-05）

## 一句话结论

调优参数已确证生效，但**"资源因此改善"这一层没有证据**——
不是收益小，是**判据在这台宿主机上无法区分信号与噪声**。
任何据此宣称"优化有效"的说法都是错的。

## 已确证的部分（可信）

| 项 | 证据 |
|:---|:---|
| 5 项参数在运行时生效 | `apply-postgres-tuning.sh` 读回 5/5 |
| 生效路径唯一且真实 | `up.sh → apply → ALTER SYSTEM → postgresql.auto.conf`；容器内 grep 确认无任何 `include` |
| 脚本幂等 | 参数全对时 `podman inspect StartedAt` 未变 |
| 缺陷可修复 | 注入 `random_page_cost=4` → 只改该 1 项并恢复 |
| 数据未受损 | 3 库 / `sys_user=1` / skywalking 247 表 |

## 未确证的部分（**本文件的存在理由**）

宿主机的实测基线：

```
MemAvailable   10.18 GB
CommitLimit    20.63 GB
Committed_AS   18.26 GB  (88.5%)
CPU 占用        77% × 12 核
外部负载        rustc 114% CPU（非容器）+ ai_developer_growth 的 pytest -n 8
```

在这种条件下测时序类指标（WALSync 次数、diskstats 设备忙时长）
**无法归因到调优参数**。

## 三次失败的量化尝试（**失败本身是结论**）

### v1：自造 TEMP TABLE 负载

```
轮1: ON=990,301   OFF=440,894   → 压缩"多"124%
轮2: ON=307,555   OFF=693,161   → 压缩"少"56%
```

**两轮结论完全相反。** 根因：查 `pg_stat_activity` 发现
**97% 的事务来自 SkyWalking OAP**（4 个来源 IP 持续
`INSERT INTO segment_tag_20261006` / `metrics_longavg_20261006`），
`cloud_infra` 库 `tup_inserted=0`。

我自造的负载只占总事务的约 3%。**造了一个"看起来相关"的负载，
测的其实是别人的噪声。**

> ⚠️ **不要把"97% 的事务"读成"97% 的 WAL"。** 前者是实测，
> 后者是推断 —— 事务数与 WAL 字节数没有固定比例（单事务大小差异很大）。
> 本文档只主张前者。同理，`cloud_infra` 库 `tup_inserted=0` 说明
> 本项目业务库当前无写入，但这不代表它**永远**不写。

### v2：改用真实负载 + 交替三轮（消除漂移）

```
轮1: ON=464,082    OFF=1,530,997
轮2: ON=1,384,703  OFF=1,810,300
轮3: ON=666,768    OFF=146,363
```

判据有效性检验：

| 组 | 中位数 | 范围 | 变异系数 |
|:---|---:|:---|---:|
| ON | 666,768 | 464,082 ~ 1,384,703 | **110%** |
| OFF | 1,530,997 | 146,363 ~ 1,810,300 | **143%** |

**两组区间完全重叠**，变异系数（110–143%）远大于组间差异。
这是判据失效的教科书形态：若连"有没有差异"都无法确定，
取中位数算出的"压缩率"就是纯噪声的产物。

## 四条可迁移的教训

1. **判据必须指向真实工作负载。** v1 自造了一个逻辑上相关的负载，
   但它只占真实写入的 3% —— 形状对了，量级错了。
   *与 AGENTS.md 第五课"探针对象必须从被测系统提取"同源。*

2. **两轮结果反向时，先怀疑判据，不要相信任何一边。**
   反向结果不是"数据有噪声，再多测几轮"，
   而是**判据根本没在测你以为的东西**。

3. **量之前先算变异系数。** 若组内方差已经覆盖组间差值，
   继续加轮次只是在噪声上做算术。

4. **"参数已生效"与"资源已改善"是两个独立结论。**
   本次只证明了前者。AGENTS.md 第三条硬规则说的正是这件事 ——
   机制存在、参数生效，都不等于业务获得了收益。

## 要得到可信结论需要什么（**当前不具备**）：

- 一台**空闲**的宿主机（无外部 rustc / pytest）
- 或一个**可隔离**的负载环境（独立 PostgreSQL 实例 + 专用数据）

注意：即便环境干净，也**不应**靠关闭 `synchronous_commit` 来制造
"改善" —— 那会牺牲断电后的数据耐久性，用真实的数据风险换一个
测出来的数字。本次刻意未改 `fsync` / `synchronous_commit`，
正是这个原因。

在上述条件具备前，本项标记为 **⚪ 无法量化**，
而非"已验证有效"或"已验证无效"。

## 附: 五个参数的 context（决定能否热切换）

`pg_settings.context` 实测：

| 参数 | context | 含义 |
|:---|:---|:---|
| `shared_buffers` | `postmaster` | **必须重启**才生效 |
| `max_wal_size` | `sighup` | `pg_reload_conf()` 即可 |
| `min_wal_size` | `sighup` | 同上 |
| `wal_compression` | `superuser` | 需超级用户，可热改 |
| `random_page_cost` | `user` | 会话级，可热改 |

这也是本次能"不重启容器"做 A/B 的原因 ——
除 `shared_buffers` 外其余四项都可热切换。
`apply-postgres-tuning.sh` 仍然重启容器，因为 `shared_buffers` 需要它；
脚本的幂等判断会先读运行时值，全部已正确时跳过重启。
