## 背景

issue 27 已把 5 项零引用能力从 `🟢 Completed` 降级为 `⚪ Built, Unused`，并写入了准入原则。
但本次追问暴露了一个**更深的问题**：降级只修正了单个条目的标记，没有修正**进度统计的口径本身**。

于是出现了一个矛盾状态：

- ROADMAP 上 M6/M7 绝大部分条目已带 `✅` 或 `✅ **...复核**` 标记
- 而这些条目按新标准全部不成立
- README 徽章仍写 `ROADMAP 45/45`、`Tests 101 passing`

**徽章看起来全绿，实际达成率 1/6。** 这正是"指标全是内部自证"的具体表现。

### 4. 本次新发现: 零引用框架已构成业务负担

`deploy/config/search-service.yaml:40-43` 至今保留:

一个业务零引用的框架, 反过来要求业务服务配置开关来规避它引入的依赖冲突。

### 5. 指标全部内部自证

README 徽章为 `Tests 101 passing` / `ROADMAP 45/45` / `ADRs 11`。

**没有一个指标指向外部**: 无"多少业务在用本平台"、无"多少接口在跑"、无"谁依赖这个骨架"。
因此"完成"在实践中被定义成"组件自测通过"。这正是过度设计的机制来源 ——
造得越多, 内部指标越好看。

## 根因

初衷假设骨架会被真实业务使用, 但项目是**演示型项目, 没有真实业务在压**。
没有需求倒逼时, 唯一推进动力变成"路线图还剩多少项", 于是自然演化成刷指标。

问题不在某一次具体决策, 而在**完成判定标准**。
前几轮一直在补窟窿(清质量门、修缺陷、冻结 gRPC), 但未质疑"为什么要往路线图加能力"这个前提。

## 已实施的变更

### 1. 完成定义升格为项目级原则 (AGENTS.md)

新增"项目级完成定义"章节, 置于准入原则之前, 明确:

- `🟢 Completed` = **被业务使用**, 判据: 业务模块存在非测试引用 + 有运行时证据
- `⚪ Built, Unused` = 代码存在且自测通过, **但不构成交付**, 不得作为完成计数
- 组件单元测试只证明能自我运转, **不是完成依据**
- 路线图进度必须同时给出两个数字: 传统口径 + 按本定义的口径

### 2. ROADMAP 新增"按被使用标准重算"章节

置于文件顶部图例之后, 常驻可见:

- 明确 M6/M7 达成率 **1/6**
- 列出每项的真实业务引用数与判定
- 声明"存量已足够, 不新增能力"的当前阶段结论

### 3. README 徽章修正

- `ROADMAP 45/45` → 标注为内部口径, 并补充外部口径说明
- `Tests 101 passing` → 更新为 429 (以 surefire XML 为准)
